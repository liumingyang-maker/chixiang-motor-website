# Chixiang Motor 国家/产品 B2B 广告落地页统一规范

日期：2026-07-30
状态：已批准设计
适用范围：国家/产品广告落地页，例如俄罗斯卧式发动机、秘鲁 CG 发动机及后续同类页面

## 1. 目标

建立一套可重复使用的静态落地页标准，让后续页面先稳定具备以下能力：

- 面向经销商、进口商、组装厂、批发商和维修渠道，主动排除普通 C 端购买意图；
- 在原始 HTML 中清楚表达公司、产品、应用、市场和采购关系，满足 SEO 与 GEO 的基础理解要求；
- 使用站内询盘表单作为第一转化路径，并在服务器确认成功后安全记录一次转化；
- 在手机、平板和桌面端保持一致结构、无裁切、无横向溢出和低布局位移；
- 使用同一套页面骨架、样式、表单和交互，先解决“有没有”，后续再逐页提高视觉完成度；
- 每次只重做一个落地页，通过独立 PR、预览和审核后再合并。

本规范不要求重构主站、不引入框架、不批量新建国家页，也不允许用模板替换国家名称后直接发布近似页面。

## 2. 页面状态与索引策略

落地页采用分级双轨。

### 2.1 正式落地页

满足事实、市场和技术门槛后，可以同时服务广告、GEO 和 SEO：

- 返回 HTTP 200；
- 使用唯一正式 URL；
- self-canonical；
- 进入 sitemap；
- 按真实语言关系提供 hreflang；
- 原始 HTML 包含完整核心内容；
- 可被搜索机器人索引。

### 2.2 测试落地页

用于尚未验证市场价值或仍缺少事实的广告测试：

- 使用 `noindex,follow`；
- 不进入 sitemap；
- 不在主导航中作为正式内容推广；
- 不得复制正式页后只更换国家名称；
- 验证商业价值并通过正式页门槛后，才能升级为可索引页面。

页面状态必须记录在实施前的 Page Brief 中，不能由开发人员临时决定。

## 3. 技术架构

采用“共享结构规范 + 每页原始 HTML 内容”。

- 保持当前静态 HTML、CSS、JavaScript 和 Cloudflare Worker 架构。
- 每个国家/产品页面拥有独立 HTML 文件和正式 URL。
- 所有页面复用一套落地页 CSS、组件类名和响应式规则。
- 所有页面复用一套表单、产品选择、折叠、移动 CTA 和追踪交互脚本。
- H1、Hero、B2B 条件、产品、参数、选型、FAQ 和公司事实直接写入页面 HTML。
- JavaScript 只能增强交互，不能从空容器开始生成首屏或核心实体内容。
- 市场配置只能保存已批准的联系方式、追踪开关和非核心交互参数，不能生成标题、正文和产品规格。
- 表单继续使用现有 `/api/contact` 与 Worker，不建立第二套提交系统。
- 不新增 React、Next.js、Vue、构建工具、GTM 或其他框架。

这一架构的核心约束是：关闭 JavaScript 后，页面仍能让搜索机器人和采购商理解“谁在供应什么、面向谁、如何询价”。

## 4. 固定模块顺序

第一版统一模板按以下顺序组织：

1. Header
2. Hero
3. B2B 采购门槛
4. 产品/型号
5. 参数与选型
6. 工厂与信任
7. FAQ
8. 询盘表单
9. Footer

### 4.1 Header

- 只保留 CHIXIANG MOTOR / CX MOTOR 品牌、主询盘按钮和必要的补充联系方式。
- 不使用完整主站导航分散广告访客。
- 主按钮滚动到当前页面表单。
- 补充联系方式不能与主按钮具有相同视觉权重。

### 4.2 Hero

首屏必须直接回答：

- 公司/品牌是谁；
- 供应什么产品；
- 面向哪个市场和哪类 B2B 买家；
- 主要应用是什么；
- 下一步如何提交采购需求。

Hero 必须包含原始 HTML H1、说明、主 CTA 和已预留尺寸的视觉区域。背景图不得嵌入标题、价格或按钮文字。

### 4.3 B2B 采购门槛

- 说明目标买家类型；
- 展示已批准的 MOQ、样品、混批或 OEM 条件；
- 没有批准数值时，要求买家提交数量和配置确认；
- 不得套用其他国家或产品的商业政策。

### 4.4 产品/型号

- 只展示当前页面意图需要的产品家族和已批准型号；
- 产品卡包含名称、用途、关键差异和选择动作；
- 不为凑数量添加未经确认的型号、排量或兼容关系；
- 产品选择可以写入询盘表单，但不能自动提交。

### 4.5 参数与选型

- 使用统一单位和字段名；
- 参数来自批准的 ENGINE_SPEC_MASTER 或同等事实源；
- 对比内容帮助采购商确认应用、冷却、挡位、启动、电气、负载和配置；
- 不保证通用兼容，要求买家提供发动机代码、车辆照片、安装位和采购数量。

### 4.6 工厂与信任

- 说明制造商身份、生产与检测能力、OEM/ODM、配件和出口支持；
- 公司成立时间、地址、证书、产能、厂房、员工和出口国家数量必须来自批准的 COMPANY_FACT_PACK；
- ISO、CCC 等只能使用批准公开的表述，不补写证书编号、范围或有效期；
- 工厂图片必须是真实可用资产，不使用无来源效果图冒充工厂证据。

### 4.7 FAQ

- 建议 5–8 个真实采购问题；
- 回答必须直接存在于 HTML；
- 重点覆盖 MOQ、样品、混批、OEM、型号确认、应用、配件、交付与询盘资料；
- 未确认的数据使用“需根据型号、配置和数量确认”，不能推测答案。

### 4.8 询盘表单

- 页面唯一主转化区域；
- 与产品选择和 CTA 来源关联；
- 明确告诉买家提交后会得到什么回复；
- 失败时保留用户已填写内容，并提供本地化错误提示和备用联系方式。

### 4.9 Footer

- 保留品牌、公司联系信息、隐私/法律链接和必要的主站入口；
- 不重复堆叠大量 CTA、产品关键词或国家名称。

## 5. GEO 与 SEO 内容规范

### 5.1 一个页面一个主实体

正式落地页的主关系为：

`国家/市场 + 产品家族或产品用途 + B2B 采购`

例如：

- 俄罗斯 + 卧式发动机 + 批发采购；
- 秘鲁 + CG 发动机 + 经销商/组装商采购。

页面不能同时竞争多个无关产品或多个国家意图。

### 5.2 原始 HTML 必须回答的问题

- Who is Chixiang Motor?
- What product is supplied on this page?
- Which applications are supported?
- Which models and configurations can be discussed?
- Which B2B buyers does the page serve?
- How are MOQ, samples, OEM, parts and delivery confirmed?
- What information should the buyer submit next?

这些答案必须存在于可见正文，Schema 不能代替正文。

### 5.3 页面所有权

- 市场落地页负责“该市场如何采购与确认产品”；
- 产品 owner 页负责“产品家族是什么、有哪些已批准型号和差异”；
- 公司 owner 页负责企业身份、工厂和能力事实；
- 落地页链接到相应公司、产品家族和目录 owner 页面；
- 支持页面不能与 owner 页面竞争完全相同的标题、H1 和搜索意图。

### 5.4 Meta 与标题

- 每页一个可见 H1；
- Title、Description 和 H1 独立编写，不能只替换国家名称；
- Title 表达产品、市场与 B2B 供应关系；
- Description 使用采购语言说明产品范围、目标买家与询价动作；
- 标题层级连续，不跳过结构层级制造视觉字号。

### 5.5 事实与证据边界

以下信息必须来自批准事实源：

- 型号、排量、冷却、挡位、启动、电气与应用；
- MOQ、样品、混批、OEM、价格与贸易条件；
- 运输方式、交付承诺与时间；
- 公司名称、成立时间、地址、认证、产能、面积、员工与出口市场；
- 市场需求、销量、买家数量、搜索量和竞争数据。

禁止使用“最畅销”“当地最受欢迎”“完全兼容”“最低价格”“全国大量需求”等无证据声明。

### 5.6 图片 SEO

- 产品图使用描述性文件名；
- alt 描述产品及其作用，不堆关键词；
- 装饰背景使用空 alt 或 CSS 背景；
- 图片中的 Logo 或型号文字不能代替 HTML 文本；
- 不在图片中嵌入不可翻译的价格、参数和 CTA。

### 5.7 Structured Data

Schema 只表达页面已经公开并确认的内容：

- Organization 使用统一公司事实；
- Breadcrumb 对应真实 URL 层级；
- FAQ 与页面可见问题和答案一致；
- Product/ProductGroup 只在产品归属和规格完成确认时使用；
- 不虚构价格、库存、评分、评价、交付时间或兼容性。

## 6. B2B 转化规范

### 6.1 默认转化层级

所有页面默认使用站内询盘表单优先：

1. 主 CTA：获取报价 / 提交采购需求；
2. 次 CTA：Email；
3. 补充渠道：按国家实际可用性配置 WeChat、WhatsApp 或其他渠道。

所有 Header、Hero、产品卡和手机固定主按钮最终进入同一个表单，不能制造多条竞争路径。

### 6.2 C 端排除

- Hero 明确面向经销商、进口商、组装厂、批发商或维修渠道；
- 表单必须收集公司、采购数量、产品和应用；
- 样品政策只能在已批准且有 B2B 限定条件时公开；
- 低价只能说明真实适用的型号、配置、数量和贸易条件；
- 不使用消费零售价吸引无法满足批量条件的买家。

### 6.3 商业政策

MOQ、样品数量、混批、OEM、价格和运输条件按产品与市场单独批准。

- 不建立一套全站通用 MOQ；
- 不把俄罗斯页面的数量规则复制到秘鲁或其他市场；
- 未批准具体数字时，只要求买家提交数量和配置；
- 页面必须说明政策适用范围，避免把样品政策解释为正式订单条件。

## 7. 表单与追踪安全

### 7.1 统一字段

第一版表单包含：

- 姓名；
- 公司名称；
- Email 或有效联系方式；
- 国家/市场；
- 产品或型号；
- 应用场景；
- 预计采购数量；
- 配置/采购要求；
- Honeypot；
- Turnstile；
- 隐藏字段：页面、语言、来源 CTA、UTM、GCLID 及批准的广告参数。

### 7.2 成功条件

只有以下链路全部完成才算一次询盘：

`前端验证通过 → Turnstile 通过 → Worker 接收 → 邮件/询盘发送成功 → Worker 返回成功`

只有 Worker 确认成功后，页面才允许：

- 显示成功提示；
- 发送 Google Ads 询盘转化；
- 发送 Yandex Metrica lead goal；
- 每个平台最多记录一次。

### 7.3 不得记录转化的情况

- 页面访问；
- 点击按钮；
- 前端验证失败；
- Honeypot 命中；
- Turnstile 失败；
- 网络失败；
- Worker 400/500；
- 邮件或询盘发送失败；
- 同一请求的重复点击。

### 7.4 错误与备用渠道

- 请求进行中锁定重复提交；
- 错误提示使用页面语言；
- 失败时恢复按钮和表单状态；
- 保留用户已填写内容；
- 显示 Email、WeChat 或 WhatsApp 等备用渠道；
- 不自动打开 WhatsApp；
- Messenger 点击只能记录为次级互动，不能冒充成功询盘。

追踪 ID、conversion label、Yandex counter 与目标名称从批准的追踪清单读取，不在新页面中凭经验复制或新建。

## 8. 统一视觉与响应式规范

### 8.1 视觉系统

- 品牌统一使用 CHIXIANG MOTOR / CX MOTOR；
- 主视觉采用深色工业底色、白色内容区和品牌红色强调色；
- 绿色仅用于 WhatsApp 等渠道标识，不作为全站主 CTA 色；
- Header、卡片、按钮、表格、表单、间距和圆角使用同一套设计 token；
- 各页面只替换语言、产品、市场事实和图片，不重新设计模块结构。

### 8.2 布局

- Header 保持最小化；
- Hero 桌面双栏、移动单列；
- 产品、参数、FAQ 和表单使用统一组件；
- 参数表在手机端转换为卡片，不能依靠横向滚动隐藏关键内容；
- DOM 顺序与阅读顺序一致，不能只依赖 CSS 调换形成不同语义。

### 8.3 验收尺寸

- 手机：390×844；
- 平板：768×1024；
- 大平板：1024×1366；
- 桌面：至少 1440×900。

各尺寸必须检查 Header、Hero、CTA、产品卡、参数、FAQ、表单和 Footer。

### 8.4 移动规则

- 不允许横向溢出、按钮裁切、文本越界或产品卡超宽；
- 不使用根节点 `overflow-x:hidden` 掩盖布局错误；
- 按钮和表单控件触控高度至少 44px；
- 手机固定 CTA 默认只保留“提交询盘”；
- 用户输入表单、打开键盘、到达表单或 Footer 时，固定 CTA 隐藏；
- 第一屏必须在手机上直接表达产品、B2B 买家和主动作。

## 9. 性能预算

- Hero 主视觉优先使用 WebP/AVIF；
- 图片提供正确 `width` 和 `height`；
- 首屏只允许一个 `fetchpriority="high"` 的关键资源；
- 首屏图片不得 lazy-load；
- 非首屏图片使用 lazy-load；
- 移动端初始页面传输目标不超过约 1.5MB；
- 单张 Hero 背景建议不超过 250KB；
- 首屏产品图总量建议不超过 300KB；
- 不引入大型组件库、重复分析脚本或无必要第三方字体。

Lighthouse 每页连续测试 3 次，以中位数验收：

- LCP 目标 ≤2.5s，第一版最低上线门槛 `<4s`；
- CLS 必须 ≤0.10；
- TBT 目标 ≤200ms；
- Performance 分数用于诊断，不以单次最高分替代指标中位数。

INP 属于真实用户现场指标，不能用实验室 TBT 冒充。上线后在 GSC Core Web Vitals / CrUX 有足够流量时观察。

## 10. 可访问性

- 一个 H1，标题层级连续；
- 图片 alt 符合真实用途；
- 链接、按钮和折叠组件可使用键盘操作；
- 焦点状态清晰；
- 文字与背景满足可读对比度；
- 表单字段有可见 label、错误关联和状态提示；
- 页面语言属性正确；
- 支持 `prefers-reduced-motion`；
- 不使用仅靠颜色表达的状态。

## 11. Page Brief

每次重做前必须完成一张 Page Brief，至少包括：

| 字段 | 要求 |
|---|---|
| 页面 URL | 正式 URL 或测试 URL |
| 页面状态 | INDEXABLE 或 TEST_NOINDEX |
| 国家与语言 | 目标市场和页面语言 |
| 主实体 | 一个产品家族或明确产品用途 |
| Owner 页面 | 对应公司、产品或目录 owner URL |
| 目标买家 | 经销商、进口商、组装厂、批发商或维修渠道 |
| 搜索/广告意图 | 买家希望解决的采购问题 |
| 产品事实 | 批准型号、参数、应用与事实 ID |
| 商业政策 | MOQ、样品、混批、OEM、价格和运输批准范围 |
| 主 CTA | 默认站内表单 |
| 补充渠道 | Email、WeChat、WhatsApp 等实际可用渠道 |
| 追踪 | Google/Yandex 需求和批准 ID |
| 图片 | 可用产品、工厂、背景与 Logo 资产 |
| 禁止声明 | 本页不得公开或仍待确认的内容 |
| 成功标准 | SEO、GEO、移动端、性能、表单与转化门槛 |

Page Brief 未完成时，不开始页面设计和代码修改。

## 12. 逐页实施流程

每次只重做一个落地页：

1. 批准 Page Brief 和事实清单；
2. 准备本地语言文案和图片；
3. 基于统一模板创建原始 HTML；
4. 本地检查手机、平板和桌面；
5. 验证表单成功、验证失败、Worker 失败和重复提交；
6. 验证普通访问和按钮点击不产生询盘转化；
7. 验证 Worker 成功后各平台最多触发一次；
8. 检查 Title、Description、H1、canonical、hreflang、sitemap 和 Schema；
9. Lighthouse 连续测试 3 次；
10. 生成桌面和移动端预览图；
11. 创建独立 Draft PR 和 Cloudflare Preview；
12. 网站所有者审核预览；
13. 明确批准后才能转为正式 PR 或合并；
14. 合并后验证正式 URL、表单和转化；
15. 不因页面上线自动扩大广告预算。

## 13. 自动与人工验收

### 13.1 自动测试

每个页面必须有回归测试保护：

- URL、canonical、hreflang 和 index 状态；
- 原始 HTML 中的 H1、主要内容和 FAQ；
- Page Brief 中批准的型号、参数和商业政策；
- 不存在禁止声明；
- 图片和资源真实存在；
- 表单字段、Honeypot 和 Turnstile；
- Worker 成功后一次转化；
- 验证、网络和 Worker 失败时零转化；
- 重复提交保护；
- 追踪 ID 与 label 未被误用；
- 页面不会产生明显横向溢出。

### 13.2 人工测试

- 390×844、768×1024、1024×1366、1440×900 截图；
- Header、Hero、CTA、产品卡、参数、FAQ、表单和 Footer；
- 键盘、焦点、表单错误和成功提示；
- 真实生产询盘邮件；
- Tag Assistant 或等效工具中的成功事件；
- Yandex Metrica 目标入账；
- Lighthouse 三轮中位数；
- Preview 与正式环境 URL/Canonical 对比。

## 14. 正式页升级门槛

测试页面只有同时满足以下条件才能升级：

- 有明确产品和市场证据；
- 原始 HTML 内容完整；
- 不是其他国家页的简单翻译；
- 一个主实体和一个明确采购意图；
- 产品和商业事实有批准来源；
- 表单与转化闭环通过；
- 三种移动尺寸无溢出；
- LCP 中位数 `<4s`；
- CLS 中位数 `≤0.10`；
- canonical、hreflang 和 sitemap 正确；
- 没有未经批准的技术或商业声明。

## 15. PR、部署与回滚

- 每个落地页使用独立分支和 PR；
- 不混入其他页面、Foundation、广告账户或 Worker 重构；
- PR 列出修改文件、事实来源、追踪位置、测试、预览和回滚方式；
- 默认创建 Draft PR，不自动合并；
- 网站所有者未批准预览时，不部署到正式网站；
- 保留替换前提交记录和仍有价值的原始图片；
- 出现表单、转化、路由、canonical 或索引故障时，可单独回滚该页面；
- 回滚后重新验证正式 URL、表单和平台事件。

## 16. 非目标

本规范不授权：

- 批量创建国家或型号页面；
- 修改广告预算、出价、关键词和账户目标；
- 修改 Worker 密钥、Turnstile Secret 或邮件凭据；
- 改造主站框架；
- 把 Messenger 点击提升为主询盘；
- 添加未经批准的产品、证书、价格、市场或物流事实；
- 因 Schema 需要而虚构 Offer、Review、Rating 或库存。

## 17. 后续使用顺序

后续逐页重做时，按商业优先级选择页面，不同时启动多个落地页。每个页面完成“Page Brief → 规范实施 → Preview 审核 → 单页合并 → 生产复核”后，再进入下一个页面。

视觉精修、动画、复杂产品筛选、案例库和高级个性化属于后续优化，不阻塞第一版统一模板建立。
